# LinkFlow 统计消息失败重试设计

## 目标

将项目展示名统一为 `LinkFlow—短链接运营平台`，并为 Redis Stream 访问统计链路增加有限重试和死信留存，避免单条异常消息无限重试或静默丢失。

## 范围

- 统计消息生产时保留稳定的业务消息键，重试消息沿用该键。
- 消费失败时按配置次数重新投递到原统计 Stream。
- 超过重试上限后写入死信 Stream，并删除原消息。
- 保留现有统计落库逻辑、幂等处理和成功消息删除行为。
- README、项目文档和简历相关说明统一使用 LinkFlow 名称。

## 非目标

- 不引入 RocketMQ 或新的消息中间件。
- 不重写现有统计落库逻辑。
- 不修改前端页面品牌和数据库表结构。

## 设计决定

- 每条统计消息使用 UUID 业务键，重试时沿用原键，幂等判断不再依赖 Redis Stream 自动生成的记录 ID。
- 重试次数写入 Stream 字段 `retryCount`，默认最多重试 3 次，可由 `short-link.stats.stream.max-retries` 配置。
- 死信 Stream 使用 `short-link:stats-stream:dead-letter`，保留原始消息、重试次数、错误摘要和失败时间。
- 重试与死信写入成功后删除原消息，避免原消息和新消息同时存在。

## 验证标准

- 首次失败会重新投递并将重试次数加一。
- 达到上限后只写入死信 Stream，不再重新投递。
- 同一业务键的重复消息仍由现有幂等处理器拦截。
- Maven 测试或可运行的最小单元测试通过，代码格式检查无新增错误。
